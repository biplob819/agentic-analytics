# M4.1 acceptance criteria

**MON-01** The scheduled smoke workflow runs `agentic-analytics smoke --max-cost 2` by hand (`workflow_dispatch`) from the `monitoring` environment's secrets (the smoke run's model keys and read-only warehouse credentials only), never on pull requests or in forks, and gates the run with `evalkit gate` on per-backend accuracy floors (`monitoring/gates.yaml`: each backend's no-fix accuracy ≥ 0.5, a missing backend an input error, a new backend gated too); the gate step is exactly the gate command under `bash -eo pipefail`, so nothing swallows its exit; secrets never sit in a workflow- or job-level `env`; the spend line the run appended (only that) goes to the job summary, never committed back; the run's metrics folder, gate verdict and spend line are uploaded as an artifact that `evalkit compare` reads; the weekly schedule is written but off until the release (OWNER D-103), and a test fails if it is switched on. *Proof:* `tests/monitoring/test_gates.py`, `tests/monitoring/test_monitor_workflow.py`, `tests/harness/test_records.py`.

**MON-02** Two runs are compared with `evalkit compare` on their metrics-1 exports, paired on shared questions through `metrics/cases.jsonl`; a regression is flagged and exits 1 with the gates file. Run history, the trend page and drift flags are MON-07 in B3.3 (OWNER D-98: they need EvalKit B5.7, v0.4.0). *Proof:* `tests/monitoring/test_compare.py`.

**MON-03** Every probe answer is scored by EvalKit `scorers.attack_outcome` (marker as canary, the MCP allow-list plus the final answer and the harness's run of the final SQL as allowed tools) beside S2.1's verdict; the verdicts agree on every golden probe answer and on all 810 stored probe answers; the six known semantic differences are pinned by tests; S2.1's verdict is the reported one, `attack_outcome` the cross-check (D-99). *Proof:* `tests/monitoring/test_probes.py`, `tests/monitoring/test_parity.py`, `docs/measurements/evalkit-parity-2026-11-17.json`.

**MON-04** `summary.json` carries `step_efficiency` per MCP configuration: mean tool calls, mean minimum (EvalKit's agent-trajectory `min_steps` idea in tool calls: answer 1, clarify 0, write probe 0, injection probe 1), mean calls beyond the minimum and the share at or under it; Cortex has none; no other summary number moves. *Proof:* `tests/monitoring/test_efficiency.py`, the golden summary.

**MON-05** Every run (and every reconcile) writes `metrics/metrics.json` in EvalKit's frozen metrics-1 format, each §6.3 metric with its interval, unit and `n`, plus EvalKit D-67's efficiency block (token means, cache-hit share, cost per case and per correct, latency p50/p95/p99, error rate, system cost; mode and price date), and the per-case sidecar `metrics/cases.jsonl`; EvalKit's own reader, `evalkit gate` and `evalkit compare` accept them; every exported name has a §6.3 row. *Proof:* `tests/monitoring/test_metrics.py`, `tests/harness/test_metric_relevance.py`, `tests/golden/metrics/`.

**MON-06** The answer-from-rows check runs from EvalKit (`evalkit.scorers.unsupported_numbers`; the local copy removed, the number reader kept for the injection check), while the clarification verdict and its bootstrap-over-questions rates stay the reported figures, with EvalKit's `clarification_rates` as the cross-check until EvalKit offers a per-question interval (OWNER D-100); both score every recorded answer identically (5,046 records of the first smoke, the baseline rescore and the fix-run rescore; every configuration's point rates), with a test on the committed measurement and on the golden run. *Proof:* `tests/monitoring/test_parity.py`, `tests/test_evalkit_contract.py`, `docs/measurements/evalkit-parity-2026-11-17.json`.
