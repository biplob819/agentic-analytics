# A2.2 — Cortex Analyst backend

**Wave 2. Depends on:** N1.4 (semantic view), N1.6, N1.2 (Snowflake executor, injected). **Unblocks:** A2.3, R3.1.

## Goal
One question through Snowflake Cortex Analyst, single turn: a key-pair-authenticated REST call with the semantic view in the body, a defensive parse of its reply, the generated SQL executed on the read-only Snowflake executor, and a schema-valid `AnalyticsAnswer` whose text is a fixed template over the executed rows (D-7), plus the API latency (D-35), the message count for cost and Cortex's warnings.

## Outputs (`agentic_analytics.backends.cortex`)
- `KeyPairJwt(account, user, private_key, *, passphrase, lifetime_s=3540, refresh_s=300, clock)` and `KeyPairJwt.from_key_file(...)`; `jwt_account`, `public_key_fingerprint`, `load_rsa_key` (CTX-01).
- `CortexClient(account, semantic_view, jwt_source, *, base_url, timeout_s=60, deadline_s=120, transport, sleep, rng)`; `account_host` with `send(question) -> bytes` (CTX-01).
- `parse_response(body) -> CortexResponse` (CTX-02).
- `template_answer(execution)` and `format_cell(value)` (CTX-05).
- `ask_cortex(question, client, executor, *, row_cap=10_000, clock) -> CortexRun(answer, cortex_messages, api_latency_ms, warehouse_elapsed_ms, warnings, execution, response)` (CTX-03..06).
- Errors: `CortexConfigError`, `CortexHTTPError`, `CortexConnectionError`, `CortexInterrupted`, `CortexTimeout`, `CortexSchemaError`.
- `tests/backends/test_cortex_live.py`: two questions through the real API and executor, `live` and skipped unless `AA_LIVE=1`.

## Decisions
- **HTTP library.** `httpx2` 2.16 (the maintained successor of httpx; `import httpx` is not installed). It is already in `uv.lock` through anthropic, openai and mcp, but only transitively: R3.1 or the owner should declare `httpx2>=2.16` in `pyproject.toml`. A new `AsyncClient` is opened per question, so the client is safe from any event loop; replies are streamed so the status is known before the body is read.
- **JWT.** RS256; `sub` = `ACCOUNT.USER`, `iss` = `sub.SHA256:<base64 sha256 of the DER SubjectPublicKeyInfo>`. ACCOUNT is the account identifier before its first dot, upper-cased (`xy12345.us-east-2.aws` → `XY12345`, `myorg-myaccount.privatelink` or `.global` → `MYORG-MYACCOUNT`; underscores kept); the user is upper-cased. The hostname keeps the full account, lower-cased, with underscores as hyphens (Snowflake URL guidance). Lifetime 59 minutes (one minute of skew under Snowflake's one-hour limit); a new token is minted once `now >= exp - 300 s`. `headers()` asks for the token on every attempt, so a retry after a long backoff never sends a stale token.
- **Secrets.** No exception message, repr or chained cause carries the JWT, the request headers, the key bytes, its passphrase or its file path: client errors name only the httpx2 exception type and are raised `from None`; key errors say `could not read/load the private key named by SNOWFLAKE_RO_PRIVATE_KEY_PATH (<type>)`.
- **Retries and deadline (§2.6).** EvalKit `with_retries`, six attempts, full-jitter backoff, all inside a total deadline (`deadline_s`, default 120 s, the agents' wall clock) on top of the 60 s per-phase httpx2 timeout. Retried, because Cortex never saw the request: connect errors and timeouts, pool timeouts, write errors and timeouts, proxy errors (`CortexConnectionError`), and 408/409/429/5xx. Never retried, because Cortex may have processed and billed it: read errors and dropped connections after sending, including mid-body (`CortexInterrupted` → `error="transport"`), and read timeouts (`CortexTimeout` → `error="timeout"`). A 200 body that cannot be decoded is `error="schema"`. Too many redirects, an unsupported protocol and any other non-200 (3xx messages point at `SNOWFLAKE_ACCOUNT`/`base_url`) raise `CortexConfigError` or `CortexHTTPError`, which `classify_error` calls `config`; `ask_cortex` re-raises them so the run stops (EK L-21). `Retry-After` is not read.
- **Parse.** Text blocks are joined; the first non-blank `sql` statement is kept with `confidence.verified_query_used` (a dict or None); `suggestions` and `suggestion` types are both read, list under either key, blanks and duplicates dropped. Content that is unknown, untyped, empty or a second `sql` is skipped and named in `CortexResponse.ignored`. If `sql` and suggestions both arrive (documented as exclusive) the SQL wins and the suggestions are recorded as ignored. `response_metadata.analyst_latency_ms` (Cortex's own time) is kept when it is a finite, non-negative number, else None, so the report can separate Cortex time from the Thailand-to-US transit (OWNER D-62). Only a body that is not a JSON object with a `message.content` list is a `CortexSchemaError`.
- **Answer mapping.** SQL → executed, `answer` = template, `interpretation` = Cortex text. Suggestions without SQL → `suggestions` kept, `sql=None`, `clarification=None`, `answer=""`. Text only (or empty content) → `error="refusal"`, the text kept as both `answer` and `interpretation` (on write probes a refusal is correct, §2.6). Unreadable or undecodable 200 → `error="schema"`, keeping the body's `request_id` when it has a non-blank one. Transport (retries exhausted, or reply lost after sending) → `error="transport"`; read timeout or deadline → `error="timeout"`; both with `sql=None`, `answer=""`. `model_snapshot` = `",".join(model_names)` or None; `request_id` from the body (blank → None).
- **Failed execution.** The SQL is kept, the answer says `The query failed (<error>).` and `answer.error` stays None: Cortex did produce an answer; S2.1 scores the failure as `sql_error`/`guard`/... from the `Execution` (§2.6 "Final SQL fails to execute"), so it is not counted twice.
- **Template (D-7).** No rows: `The query returned no rows.` One cell: `The result is <v>.` One row: `COL1: v1, COL2: v2`. More rows: `<n> rows returned; first: COL1: v1, ...`, n = rows held (what answer-from-rows counts), with `(cut at the row cap)` when truncated. Cells are written exactly: integers in full with no separators, floats as their shortest exact decimal with no exponent (`1e-05` → `0.00001`), `NULL`, `true`/`false`, strings unchanged, lists as JSON. Numeric cells therefore pass answer-from-rows by construction (tested against S2.1's `unsupported_numbers` while that module is present).
- **Execution.** `executor.execute(sql, row_cap=10_000)` through a local `SqlExecutor` protocol (backends never import `warehouse/`); R3.1 passes the `SnowflakeExecutor` under `ANALYTICS_RO`, whose SQL guard runs first. An Execution from another engine is a wiring bug (`TypeError`); executor exceptions (e.g. `WarehouseConfigError`) propagate. The call is synchronous (the connector is), so it blocks the event loop for the query's duration.
- **Counts and timing.** `cortex_messages` = 1 when the API answered 200 (billed per successful message) or when the request may have reached Cortex before the reply was lost (read error, read timeout, or the deadline firing while a request was in flight): counted conservatively for cost. It is 0 when no request got past connecting or every reply was a non-billed status (deadline during backoff included). `api_latency_ms` covers the whole API call on the injected clock, retries and backoff included (what a user waits), on every path, success or failure, and excludes execution; `warehouse_elapsed_ms` is the executor's `elapsed_ms` (0 when nothing ran).

## Live findings (2026-11-16)
- Real replies are recorded in `tests/backends/fixtures/cortex/` (request ids redacted, also inside the SQL comment Cortex appends) and the offline tests run over them (`test_cortex_recorded.py`, EK L-17).
- Cortex writes semantic SQL: `SELECT * FROM SEMANTIC_VIEW(<view> METRICS ... DIMENSIONS ... WHERE ...)`, sometimes inside CTEs, with `response_metadata.is_semantic_sql` true. The N1.2 Snowflake guard refused it, so every Cortex answer failed as `guard`; fixed in `warehouse/guard.py` (Snowflake only, FROM/JOIN source only, unquoted and unqualified keyword, the view a plain `DATABASE.SCHEMA.VIEW` of three identifiers; inner expressions still checked).
- With the runner's as-of line (`run/runner.py` `cortex_question`, D-10) Cortex resolves relative dates from the as-of date, not `CURRENT_DATE`: verifier re-ask of q-118 ("last month") gave July 2026 via `'2026-08-31'::DATE`, q-101 ("last year") gave `YEAR(date) = 2025`. The builder's raw-question calls, which used `CURRENT_DATE`, do not reflect the run.
- Declines (a write probe, a question the data cannot answer) arrive as text plus suggestions with `question_category` UNCLEAR, not text alone, so they map to the suggestions path (a clarification, nothing executed). Write probes still pass because nothing ran (S2.1 policy); the `refusal` path stays for text-only replies.
- Error bodies: 400 and 404 carry `error_code` (`390400`, `390404`), `code: null` and a request id; 401 carries `code: "390144"` and no request id.

## Gaps
- Cortex runs with the RO user's default role as primary role. Live, `AA_RO_USER` has `DEFAULT_ROLE` null, so the primary role is PUBLIC and `ANALYTICS_RO` is reached only through `DEFAULT_SECONDARY_ROLES = ('ALL')` (the 404 body says "Your primary role PUBLIC"). It works, since ANALYTICS_RO is the user's only granted role, but the N1.7 bootstrap's `ALTER USER AA_RO_USER SET DEFAULT_ROLE = ANALYTICS_RO DEFAULT_WAREHOUSE = ANALYTICS_XS` has not been applied to the live account (owner action: re-run `agentic-analytics setup snowflake --run`, or that one statement as ACCOUNTADMIN).
- Digits inside text cells (addresses) may be flagged by answer-from-rows; S2.1's number check handles it, the template stays as is.
