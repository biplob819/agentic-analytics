# N1.2 — Read-only executors

**Wave 1. Depends on:** N1.1. **Unblocks:** N1.3, Q2.2, S2.1, A2.2.

## Goal
One read-only executor per engine that every backend's final SQL goes through (D-3), behind four read-only layers (D-19): the SQL guard, the ClickHouse role, the Snowflake role, and (in N1.5) the MCP allow-list. Every execution returns a typed `Execution` with `elapsed_ms` and a query id, and never raises for a warehouse error.

## Outputs
- `agentic_analytics.warehouse.guard.check_sql(sql, engine) -> GuardVerdict(ok, reason)` (EXE-01).
- `ClickHouseExecutor(host, user, password, *, client=None)` over clickhouse-connect (EXE-02).
- `SnowflakeExecutor(account, user, private_key_path, warehouse, role, *, connect=None)` over snowflake-connector-python with key-pair (JWT) auth (EXE-03).
- `roles.clickhouse_role_sql`, `roles.snowflake_role_sql`, `roles.pack_role_sql(pack, engine)` and the checker `roles.role_sql_problems(sql, engine)` (EXE-04).
- `_common.to_json_value`, the `Executor` protocol (§4), `WarehouseConfigError`, `ROW_CAP = 10_000` (EXE-02, EXE-03, EXE-05).
- `doctor.run_doctor(environ, *, clickhouse=None, snowflake=None, pack=None) -> DoctorReport` and `doctor.executors_from_env(environ)` (EXE-06). The CLI command is wired in `cli.py` separately.

## Design decisions
- **Guard policy (allow-list over the sqlglot tree, never keyword search).** Exactly one statement whose root is `SELECT`, a set operation (`UNION`/`INTERSECT`/`EXCEPT`) or a parenthesised query; `WITH` rides on these. Refused: any DDL/DML/command node anywhere, `SET`, `USE`, `SYSTEM`, `GRANT`/`REVOKE`, `CALL`, `COPY`/`PUT`/`GET`/`LIST`/`REMOVE`, `SHOW`, `DESCRIBE`, and **`EXPLAIN`** (harmless, but its output is not a result the scorer compares, so not worth the surface). Any `INTO` token (`INTO OUTFILE`, Snowflake `INTO :var`), a ClickHouse `SETTINGS` clause (the executor owns settings, so `readonly` cannot be lowered from SQL) and a `FORMAT` clause are refused. Table functions are refused unless they only generate rows (ClickHouse `numbers`, `zeros`, `generateSeries`; Snowflake `FLATTEN`, `SPLIT_TO_TABLE`, `GENERATOR`). Functions that reach files, the network, other servers, external engines, processes, dictionaries, stages or the control plane are refused in any position (`url`, `s3*`, `file`, `remote*`, `cluster*`, `input`, `jdbc`, `odbc`, `mysql`, `postgresql`, `hdfs`, `azureBlobStorage`, `gcs`, `iceberg*`, `deltaLake`, `hudi`, `executable`, `dictionary`, `dictGet*`, `SYSTEM$*`, `GET_PRESIGNED_URL`, `INFER_SCHEMA`, `RESULT_SCAN`, ...). Schema-qualified calls (`db.fn(x)`, i.e. UDFs and external functions) and Snowflake stage references (`@stage`, `@~`, `@%t`) are refused. Control and invisible characters (zero-width, bidi overrides, NUL) are refused before parsing; function names are NFKC-normalised and case-folded. Parse failures, empty input and comment-only input are refusals.
- **Verifier round 1 fixes:** `SETTINGS`/`FORMAT` are checked on every query node and at token level; quoted stage paths (`FROM '@~/f.csv'`), any string-literal table, `@`-prefixed literals and `$n` columns are refused on Snowflake; Cortex AI functions and every ClickHouse `dict*` function are denied; the ClickHouse `system` database is refused (`information_schema` allowed); `SELECT 1; -- note` is one statement; ClickHouse errors are classified by numeric code only; maps convert to sorted `[key, value]` pairs; doctor compares the Snowflake session role with `ANALYTICS_RO` and withholds any detail that still contains a short secret value. Known limitation: sqlglot cannot parse ClickHouse `LIMIT n BY x LIMIT m`, so it is refused (a safe false positive; wrap the query and put the outer LIMIT outside).
- **Verifier round 2 fixes:** inside `ARRAY JOIN (subquery)` sqlglot reads the inner FROM as a column, so every FROM/JOIN target anywhere in the tree must now be a table, subquery, VALUES or allowed table function, ARRAY JOIN over a subquery is refused, and a token backstop refuses `FROM`/`JOIN name(` for non-generators; `system`-qualified references are refused anywhere (`IN system.users`); introspection functions are denied; deny-listed names match function calls only; Snowflake `@` is refused in table position only and `$1` is allowed; ClickHouse `SETTINGS`/`FORMAT` are told apart from columns of those names; nested block comments are refused; the count query drops trailing semicolons and comments.
- **Verifier round 3 fixes:** an unknown function on the right of `IN` (a ClickHouse table function there) is refused unless it is a row generator; the FROM/JOIN token backstop skips `ARRAY JOIN` expressions; only `/*` inside block comments counts as nesting; `TO_FILE` is denied with the other stage-file functions.
- **Verifier round 4 fix:** the round-3 rule for the right of IN was position-based and both missed `notIn(a, s3Queue(...))`-style forms and over-refused `IN (today())`. It is replaced by a name rule: a call to any documented ClickHouse table function is refused anywhere except a row generator used as its own FROM/JOIN source. **Known limitation:** a future table function not yet in the list is allowed outside FROM/JOIN (e.g. `x IN newFn(...)`); the read-only role, which holds no SOURCES grants, still refuses external access at the server.
- **A2.2 live fix (2026-11-16):** Cortex Analyst writes semantic SQL, `SELECT * FROM SEMANTIC_VIEW(db.schema.view METRICS ... DIMENSIONS ... WHERE ...)`, which the guard refused (token backstop and tree), failing every Cortex answer as `guard`. Snowflake `SEMANTIC_VIEW` (sqlglot `exp.SemanticView`) is now allowed as a FROM/JOIN source when the view is a plain `DATABASE.SCHEMA.VIEW` name (three non-empty identifiers, nothing else); anywhere else, on ClickHouse, quoted (`"SEMANTIC_VIEW"(...)`, a UDF), schema-qualified (`db.s.SEMANTIC_VIEW(...)`, a UDF), or when any part of the view name is a literal, stage, parameter, `IDENTIFIER(...)` or carries `AT(...)`, it is refused; its metric, dimension and WHERE expressions go through every other check. The A2.2 verifier found the first version checked only the last name part and the parent, so `IDENTIFIER('a.b.c').x`, `a.IDENTIFIER('b').c`, `db.s.SEMANTIC_VIEW(...)` and `"semantic_view"(...)` passed (sqlglot's function parser matches the upper-cased name whatever its quoting or qualifier); a differential run of HEAD's guard against this one over every string literal in `tests/` (6,610 strings, both engines) differs only on `SEMANTIC_VIEW` strings, all on Snowflake. Tests: `tests/backends/test_cortex_recorded.py` (recorded Cortex SQL, one refusal per rule).
- **sqlglot quirk found while building:** `FROM dictionary('d')` parses as table `dictionary` with alias columns `('d')`. The guard refuses table names on the deny list and, on ClickHouse, any alias-column list without an alias name (ClickHouse has no such syntax), so that shape is always treated as a table function.
- **Truncation and `rows_total`.** ClickHouse: `max_result_rows = row_cap + 1` with `result_overflow_mode = 'break'` stops the server just past the cap (whole blocks, so possibly more rows); the client keeps `row_cap` rows. When rows were cut, a second guarded query `SELECT count(*) FROM (<sql>)` gives the exact `rows_total`. Snowflake: `fetchmany(row_cap + 1)` with `cursor.rowcount`, which is the exact size of the full result, so no second query; the count query is the fallback when the driver gives no rowcount. If the count itself fails, `rows_total = row_cap + 1`, a lower bound, with `truncated = True` (the `Execution` invariant `truncated == len(rows) < rows_total` still holds).
- **Settings on ClickHouse.** `max_execution_time = 30`, `max_result_rows`, `result_overflow_mode`, then `readonly = 1` last. Settings the server profile has locked for the user (seen through `client.server_settings`) are left to the profile, because clickhouse-connect refuses to send them; the profile's `CHANGEABLE_IN_READONLY` constraints let the executor lower its own limits. Sending `readonly = 1` per query also protects a misconfigured non-readonly user. The client is built with `query_limit = 0` so the driver never appends a `LIMIT`.
- **Value conversion (deterministic, JSON-safe).** `None`/`bool`/`str`/`int` pass through (big ints stay exact); finite floats pass, NaN and infinities become `None` (ClickHouse `avg` over nothing is `nan` where Snowflake gives NULL); `Decimal` becomes `int` when integral (exact) and otherwise the nearest `float` (about 15-17 significant digits, far inside every tolerance, rel 1e-6); non-finite decimals become `None`; `date` → `YYYY-MM-DD`; naive `datetime` → ISO 8601 as returned; aware `datetime` → UTC ISO 8601 with `+00:00`; `time` → ISO; `timedelta` → seconds; `UUID`, IPv4/IPv6 → canonical string; `bytes` → base64; arrays/tuples → lists, maps → lists of `[key, value]` pairs sorted by the key's JSON text, sets → sorted lists; anything else → `str(value)`.
- **Errors.** Warehouse errors never raise and ClickHouse errors are classified by numeric code only: timeouts (ClickHouse codes 159/160/209/394, Snowflake errno 604/630 or SQLSTATE 57014) → `timeout`; connection and network failures → `transport`; everything the server rejects (syntax, permissions, missing objects, client-side driver refusals) → `sql_error`; guard refusals → `guard`. **Deliberate exception:** rejected credentials (ClickHouse 516/192/194, Snowflake 3901xx) and unreadable key files raise `WarehouseConfigError`, because config errors must stop a run rather than be scored (EK L-21). A non-positive `row_cap` is a programming error (`ValueError`).
- **`elapsed_ms` and query id (EXE-05).** `elapsed_ms` is wall-clock time for the whole `execute` call (guard, query and any count) from an injectable clock. ClickHouse: the executor generates `aa-<uuid4>` and sends it as `query_id`, so the id is recorded even when the query fails; the server's id is used when it reports one. Snowflake: `cursor.sfqid`, or the error's `sfqid` on failure. `query_id` is `None` only when nothing was sent (guard refusal, no connection).
- **Role SQL** lives in `roles.py` as engine templates parameterised by the pack (`databases[engine]` plus `<name>_probes`); identifiers are validated so a pack cannot inject SQL. ClickHouse: settings profile `analytics_ro_profile` (`readonly = 1`, `max_execution_time = 30 MAX 30`, result limits changeable in readonly), role `analytics_ro` bound to it, `GRANT SELECT ON <db>.*` for the pack and probes databases, nothing else (no `SOURCES`, `URL`, `REMOTE`). Snowflake: role `ANALYTICS_RO`; XS warehouse `AUTO_SUSPEND = 60 AUTO_RESUME = TRUE INITIALLY_SUSPENDED = TRUE` (re-asserted with `ALTER` when it exists); USAGE on warehouse, database and schemas; SELECT on all and future tables; SELECT on all and future semantic views; database role `SNOWFLAKE.CORTEX_ANALYST_USER`. Creating the users (password / RSA public key) and binding the ClickHouse Cloud MCP Query API endpoint to `analytics_ro` are console steps, checked live by `doctor` in the measurement node.
- **Doctor** reports env var names as set or missing (blank counts as missing) and never stores a value; driver error text is scrubbed of every environment value. With executors it checks: reachable; the guard refuses a write and `url()` (or a stage read) before sending; the server refuses `INSERT ... SELECT ... LIMIT 0` (harmless even if accepted) and `CREATE TABLE` (dropped again if accepted) and, on ClickHouse, `SELECT * FROM url(...)`, all sent raw with no per-query settings so the role and profile are what is tested; ClickHouse profile reads back `readonly = 1`, `max_execution_time <= 30`; Snowflake session role is `ANALYTICS_RO` and `SHOW WAREHOUSES` reads back `AUTO_SUSPEND` in 1..60 with `AUTO_RESUME`. The ClickHouse Cloud idle timeout has no SQL read-back, so that check is `skip`.
