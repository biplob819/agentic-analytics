# N1.2 acceptance criteria

**EXE-01** `check_sql(sql, engine)` returns `GuardVerdict(ok=True)` only when the input parses in the engine's sqlglot dialect to exactly one statement (a trailing `;` followed only by whitespace or comments is allowed) whose root is `SELECT`, a set operation or a parenthesised query, and otherwise `ok=False` with a reason naming the rule. Guarantees, each with its own isolating test: (a) no DDL, DML, command, `SET`, `USE`, `SYSTEM`, `GRANT`, `CALL`, `COPY`/`PUT`/`GET`, `SHOW`, `DESCRIBE` or `EXPLAIN` node anywhere in the tree; (b) no `INTO` token and no nested block comment (`/*` inside a `/* ... */` comment; `/*` inside a `--` line comment is allowed) anywhere; (c) on ClickHouse no `SETTINGS` or `FORMAT` clause on any query node (SELECT, UNION/EXCEPT/INTERSECT, parenthesised subquery, CTE), checked on the tree and, independently, on the token stream (`SETTINGS name =`, or `FORMAT Name` ending a query), while columns named `format`, `settings` or `system` stay allowed; (c2) every FROM and JOIN anywhere in the tree, including ones nested under expressions, targets a table, a subquery, VALUES or an allowed table function, anything else (a parser shape the guard does not understand) is refused, ARRAY JOIN over a subquery is refused, and a token backstop refuses `FROM`/`JOIN` followed by any `name(` that is not a row generator (except after `ARRAY`, so `ARRAY JOIN splitByChar(...)`, `arrayEnumerate`, `range`, `arrayMap` stay allowed); (c3) on ClickHouse a call to any documented table-function name (a static list of every one in the ClickHouse docs, case-insensitive, plus the `iceberg`/`deltaLake`/`hudi`/`paimon` families) is refused anywhere in the query, in any position, nesting or parentheses, including `IN`, `GLOBAL IN` and the `notIn`/`globalIn`/`globalNotIn`/`nullIn`/`notNullIn`/`globalNullIn`/`globalNotNullIn` function forms, except a row generator (`numbers`, `numbers_mt`, `zeros`, `zeros_mt`, `generateSeries`, `primes`, and `values`, which sqlglot parses as a VALUES node) used as its own FROM/JOIN source (`null` and `view` stay refused everywhere); the list is pinned in a test against the ClickHouse docs table-functions list fetched 2026-11-15 and every documented name is refused as a call inside `IN`/`notIn`; `format` is left out because it is also a string function; scalar calls on the right of `IN` (`IN (today())`, `IN (toDate('2024-01-01'))`, `IN (toYear(now()))`, `IN (toYYYYMM(today()))`, `IN (lower('x'))`) are allowed; known limitation: a future table function missing from the list is allowed outside FROM/JOIN, mitigated by the read-only role holding no SOURCES grants; (d) every table function is refused unless it is a row generator (ClickHouse `numbers`, `numbers_mt`, `zeros`, `zeros_mt`, `generateSeries`; Snowflake `FLATTEN`, `SPLIT_TO_TABLE`, `STRTOK_SPLIT_TO_TABLE`, `GENERATOR`), so unknown and future ones (`s3Queue`, `ytsaurus`) are refused; (e) outside-reaching and introspection functions are refused as function calls in any position (deny-listed names used as plain table or column names, e.g. `uk.input`, `uk.dictionary_terms`, `ANALYTICS.UK.SENTIMENT`, `PROMPT`, are allowed) after NFKC normalisation and case folding (`url`, `s3*`, `file`, `remote*`, `cluster*`, `input`, `jdbc`, `odbc`, `mysql`, `postgresql`, `hdfs`, `azureBlobStorage`, `gcs`, `iceberg*`, `deltaLake`, `hudi`, `executable`, `dictionary`, every `dict*` function including `dictIsIn`, `SYSTEM$*`, stage and file URL functions, `INFER_SCHEMA`, `RESULT_SCAN`, `hasColumnInTable`, `getSetting`, `getMacro`, `currentRoles`/`currentProfiles` and similar, `catboostEvaluate`), and on Snowflake every Cortex AI function (`AI_*`, `COMPLETE`, `SUMMARIZE`, ...) and every stage-file function (`TO_FILE`, `BUILD_SCOPED_FILE_URL`, `BUILD_STAGE_FILE_URL`, `GET_STAGE_LOCATION`, `GET_RELATIVE_PATH`, `GET_ABSOLUTE_PATH`, `GET_PRESIGNED_URL`); (f) schema-qualified function calls are refused; (g) on Snowflake, tables named by a string literal (`FROM '@~/f.csv'`), identifiers starting with `@` and `@stage` expressions are refused, while `@` inside ordinary strings (`LIKE '@%'`) and numeric positional columns (`$1`) are allowed; (h) on ClickHouse, any table or column reference qualified by the `system` database is refused anywhere, including `x IN system.users` and `GLOBAL IN`, on the tree and at token level (`system .`); `information_schema` stays allowed for schema discovery; (i) control and invisible characters, empty, comment-only and unparseable input are refused. The corpus holds at least 40 hostile and 40 benign ClickHouse statements plus Snowflake ones, every hostile one refused and every benign one allowed; a hypothesis property shows no read joined to a write by any separator is allowed. Known false positive: ClickHouse `LIMIT n BY x LIMIT m` does not parse in sqlglot and is refused.
**EXE-02** `ClickHouseExecutor.execute(sql, row_cap=10_000)` runs `check_sql` before the client and never calls the client for refused SQL; it sends `max_execution_time=30`, `max_result_rows=row_cap+1`, `result_overflow_mode='break'`, `readonly=1` (last) and a generated `query_id`, leaving settings the server profile has locked to the profile, and builds the client with `query_limit=0`; it returns an `Execution` whose `ResultSet` holds JSON-safe values converted as the spec documents (Decimal, date, datetime, UUID, IPv4, NaN, bytes, maps as sorted `[key, value]` pairs so keys `1` and `"1"` never collide) and round-trips through JSON; more than `row_cap` rows give `row_cap` rows, `truncated=True` and the exact `rows_total` from a guarded count query, or the lower bound `row_cap + 1` if the count fails (the count body ends at the last real token, so `SELECT ...; -- c` still counts exactly); errors are classified only by the numeric ClickHouse code (the driver's `code` attribute, else a `Code: NNN` / `code: NNN` prefix at the start of the message, never words elsewhere in it): 159/160/209/394 or a socket timeout give `timeout`, network failures `transport`, other server errors `sql_error`, all without raising, and only codes 516/192/194 raise `WarehouseConfigError`, so a query echoing `AUTHENTICATION_FAILED` is an `sql_error`.
**EXE-03** `SnowflakeExecutor` connects once, lazily, with `authenticator="SNOWFLAKE_JWT"`, the PEM key (optionally encrypted) loaded into PKCS#8 DER bytes, the given role and warehouse, and session parameters `STATEMENT_TIMEOUT_IN_SECONDS=30`, `MULTI_STATEMENT_COUNT=1` and `QUERY_TAG`; it guards first and never connects for refused SQL; it fetches `row_cap + 1` rows, reports the exact `rows_total` from `cursor.rowcount` (falling back to a count query, then to the lower bound), returns `query_id` = `sfqid` (from the error on failure), maps errno 630 or 604, or SQLSTATE 57014 on its own, to `timeout`, `OperationalError` to `transport` and other connector errors to `sql_error`, closes every cursor, and raises `WarehouseConfigError` for a missing or undecryptable key or a 3901xx login error.
**EXE-04** `pack_role_sql(pack, engine)` renders, for the pack's databases plus `<name>_probes`: on ClickHouse a settings profile with `readonly = 1` and `max_execution_time = 30 MAX 30`, role `analytics_ro` bound to it and `GRANT SELECT ON <db>.*` only; on Snowflake role `ANALYTICS_RO` with USAGE on the warehouse, database and schemas, SELECT on all and future tables and semantic views, `DATABASE ROLE SNOWFLAKE.CORTEX_ANALYST_USER`, and an XSMALL warehouse with `AUTO_SUSPEND = 60`, `AUTO_RESUME = TRUE` and `INITIALLY_SUSPENDED = TRUE`; no rendered GRANT carries ALL, a write, SOURCES/URL/REMOTE, OWNERSHIP, CREATE, MODIFY, OPERATE or a grant option; non-identifier names raise `ValueError`; `role_sql_problems` returns nothing for the rendered SQL, at least one problem for each of 12 planted ClickHouse and 16 planted Snowflake defects, and specifically a `grant option` problem for `WITH GRANT OPTION` on either engine.
**EXE-05** Every `Execution` from either executor carries an integer `elapsed_ms` measured from an injectable clock around the whole call (success, guard refusal and every error kind), and a query id whenever SQL was sent: the server's or the generated id on ClickHouse (also on failure), `sfqid` on Snowflake (also from the error); the id is `None` only for guard refusals and connection failures.
**EXE-06** `run_doctor(environ, ...)` lists all 21 Tech Spec §4 variables (checked against the spec table, not the module's list) as set or missing, blank counting as missing, and no value of a §4 variable or of any secret-looking variable, even one outside §4, (name containing KEY, SECRET, PASS, TOKEN, CREDENTIAL, DATABASE_URL or DSN) ever appears in `render()` or `to_json()`: values of 4+ characters are masked wherever they occur in driver text, and if a shorter value still occurs the whole detail is withheld; other environment variables never hide details. With injected executors it reports pass/fail/skip for: engine reachable, guard refuses a write and `url()`/stage read without sending (fails if the guard lets them through or if a `guard` error still carries a query id), the server refuses `INSERT ... LIMIT 0`, `CREATE TABLE` (and on ClickHouse `url()`) sent raw without per-query settings, the ClickHouse profile reads back `readonly = 1` and `max_execution_time` in 1..30, the Snowflake session role equals the constant `ANALYTICS_RO` (whatever role the executor was given), and `SHOW WAREHOUSES` reads back `AUTO_SUSPEND` in 1..60 with `AUTO_RESUME`; planted misconfigurations (write accepted, `url()` reaching the network, readonly 0, long timeout, AUTO_SUSPEND 3600/0/NULL, auto-resume off, wrong role) each fail the report, missing engines are `skip`, and a config error is reported, not raised.
