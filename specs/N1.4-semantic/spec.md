# N1.4 — Semantic layer

**Wave 1. Depends on:** N1.3. **Unblocks:** A2.2 (Cortex Analyst reads the view), F3.1 (the `descriptions` fix is the prompt block).

## Goal
One semantic source per pack, `packs/<pack>/semantic.yaml`, generates both the Snowflake semantic view that Cortex Analyst reads and the "descriptions" prompt block that the MCP agents get as a fix, so "agent + descriptions vs Cortex" compares two systems given the same information (D-8, C6). ClickHouse column comments are never used: they would leak into the baseline. This half is the offline build; creating the view on the trial account and granting it to `ANALYTICS_RO` is the live half.

## Outputs
- `packs/uk_price_paid/semantic.yaml`, the single source (SEM-01). The owner reviews it.
- `agentic_analytics.semantic.model`: `SemanticModel` (strict, frozen pydantic), `parse_semantic`, `load_semantic(pack)`, `pack_table_columns(pack, table)`, `check_columns`, `comment_text`, `SemanticError` (SEM-01).
- `agentic_analytics.semantic.snowflake`: `semantic_view_ddl(model, view_name, table_fqn)` (SEM-02), `parse_semantic_view_ddl(ddl)` (the reader the parity check uses), `default_names(pack, model)`.
- `agentic_analytics.semantic.prompt`: `descriptions_block(model)`, `parse_descriptions_block(block)`, `semantic_hash(model)` (SEM-03).
- `agentic_analytics.semantic.parity`: `semantic_parity(ddl, block)`, `require_semantic_parity`, `SemanticParityError` (SEM-04).
- Tests in `tests/semantic/`, golden files in `tests/semantic/golden/`, live proofs in `tests/semantic/test_live.py` (marked `live`).

## Design decisions
- **SEM-01** The model has one table (the pack's benchmark table), dimensions (categorical or time; a time dimension may carry a `year` or `month` transform), facts (a numeric column) and metrics (`count`, `sum`, `avg` or `median` of a fact). Every item has a plain-English description and may have synonyms and sample values. Names are lowercase identifiers, unique across the whole view; synonyms are unique (casefolded) across the view and never equal an item's name; descriptions, synonyms and sample values are single-line text: no control characters and nothing `str.splitlines` would split on. `load_semantic` also checks the model against the pack's load SQL: every column must exist in the table's `CREATE TABLE` on every engine the pack has (and the engines must agree on the column list), facts must be numeric on every engine, and time dimensions and transforms must sit on a date column.
- **One comment text.** Snowflake's semantic view DDL has a comment and synonyms per item but no sample values, so an item's *comment text* is its description followed by `Sample values: a, b, c.` when it has any. The DDL `COMMENT` and the prompt block's `Description:` line are both exactly this text, so Cortex and the agents see the same sample values (C6).
- **SEM-02** `semantic_view_ddl` writes `CREATE OR REPLACE SEMANTIC VIEW <view> TABLES (…) FACTS (…) DIMENSIONS (…) METRICS (…) COMMENT = '…'` to the grammar in Snowflake's `CREATE SEMANTIC VIEW` reference: one logical table aliased by the model's table name with `WITH SYNONYMS = (…)` and `COMMENT = '…'`, each fact, dimension and metric as `<alias>.<name> AS <expr>` with its synonyms and comment. Derived dimensions are `YEAR(col)` and `DATE_TRUNC('MONTH', col)`; metrics are `COUNT`, `SUM`, `AVG` and `MEDIAN` (exact in Snowflake) over the fact's column. String literals double single quotes and backslashes (Snowflake interprets backslash escapes in single-quoted literals). The view and table names must be `DATABASE.SCHEMA.NAME` of plain identifiers. The grammar lives in this one function; the exact DDL is checked on the live account at the N1.4 live step. Granting is already covered by the N1.2 role SQL (`GRANT SELECT ON ALL | FUTURE SEMANTIC VIEWS IN SCHEMA`); `semantic_view_grant_sql` gives the explicit per-view grant for the live step.
- **SEM-03** `descriptions_block` is the exact text the `descriptions` fix injects: an overview (the view comment), the table with its description and synonyms, then every dimension, fact and metric with its column (or derivation, or aggregation), its comment text and its synonyms, in source order. It is a pure function of the model, so it is deterministic. `semantic_hash` is the sha256 of the canonical JSON of the validated model (sorted keys, compact separators, defaults filled), so YAML layout and comments do not change it and any change to content does.
- **SEM-04** `semantic_parity(ddl, block)` parses *both generated texts back* (a quote-aware tokenizer for the DDL; a line reader for the block), never the model, so a generator bug in either is caught. Every item (view, table, each fact, dimension and metric) must appear in both with the identical comment text and the same synonym set, and each fact, dimension and metric must have the same source (the block's `Column:` or `Aggregation:` line against the DDL expression, both read into one form such as `year of column date`); anything present in only one, or different, is an issue. Metrics aggregate the fact by name on both sides.

## Offline vs live
Offline (this half): every criterion above, on the bundled pack and on small fixture models. Live (needs the Snowflake trial account): run the generated DDL as the admin role, grant it to `ANALYTICS_RO`, read it back with `DESCRIBE SEMANTIC VIEW`, and check every sample value exists in the loaded table. `tests/semantic/test_live.py`, skipped unless `AA_LIVE=1`.

## Out of scope
Wiring the block into the agent prompt (F3.1), the Cortex client (A2.2), `pack check` calling `load_semantic` (QST-08 owns `pack check`; it may call it later), the CLI step that creates the view.
