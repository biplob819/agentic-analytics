# N1.7 — Account setup command

**Wave 1. Depends on:** N1.2. **Unblocks:** nothing in the graph; it makes the live halves of N1.2, N1.3 and A2.1 one command each (OWNER D-55).

## Goal
`agentic-analytics setup clickhouse` and `agentic-analytics setup snowflake` (alias `aa`) provision both engines for any user from the terminal, write `.env` without ever showing a secret, and leave only the steps with no public API (signup, the MCP toggle, the Query API endpoint binding) to the web, printed word for word. `doctor` then proves the one binding nothing else can check: MCP queries run as `analytics_ro`.

- `agentic_analytics.setup.clickhousectl`: `Clickhousectl` (every call `clickhousectl cloud … --json`), `Runner`, `Completed`, `find_clickhousectl`, `subprocess_runner` (SET-01, SET-02).
- `agentic_analytics.setup.snowflake`: `ensure_keys`, `bootstrap_sql`, `setup_snowflake`, `verify_key_logins`, `clean_account` (SET-06).
- `agentic_analytics.setup.envfile`: `update_env_file`, `read_env_file` (SET-04).
- `agentic_analytics.setup._common`: `SecretBox`, `SetupError`, the tolerant JSON helpers (SET-01, SET-04).
- `agentic_analytics.setup.cli`: `add_setup_args`, `cli_setup`; `cli.py` gets the `setup` entry in `COMMANDS` and `BUILT`.
- `warehouse.doctor`: `mcp_checks`, `mcp_query`, `mcp_query_from_env`, and `run_doctor(..., mcp=, check_mcp=)`; `cli doctor` runs the check whenever the MCP variables are set (SET-07).

## Design decisions
- **clickhousectl, never a secret on a command line.** Every Cloud call goes through `clickhousectl cloud <args> --json` with an injected runner. `clickhousectl` resolves the admin Cloud API key itself (`--api-key` is never passed): saved credentials from `cloud auth login --interactive` in `./.clickhouse/` (git-ignored), else `CLICKHOUSE_CLOUD_API_KEY` / `CLICKHOUSE_CLOUD_API_SECRET` from the shell or `.env`. Exit 4 becomes a login hint. Telemetry is off for the child (`DO_NOT_TRACK=1`, documented by `clickhousectl telemetry --help`).
- **Tolerant JSON.** The `--json` shapes are not pinned, so fields are found by any of several spellings at any depth (`result` wrapper or flat; `keyId`/`key_id`; the `https` endpoint's host). A missing field is a `SetupError` that lists the key names seen, never values. The key id is read only from `keyId`-like fields, never from the management `id`.
- **Service (SET-01).** Adopt by exact name from `service list` (two services with the name are refused); otherwise `service create --name N --provider aws --region R [--ip-allow …]` (`--region` is required only to create). The default user's password is printed once, so it is written to `.env` before the id is even validated. `service get` is polled (injected `sleep`/`clock`, default 15 min, 10 s) until `running` or `idle`; `stopped` is started once; `failed`/`terminated` stop. An adopted service needs `CLICKHOUSE_ADMIN_PASSWORD` in `.env`, or `--reset-admin-password` (`service reset-password`, which changes the default user's password, hence opt-in). With no `--ip-allow`, a note says the service is open to anywhere.
- **MCP key (SET-02).** Kept when `CLICKHOUSE_MCP_KEY_ID` and `CLICKHOUSE_MCP_KEY_SECRET` are set, unless `--rotate-mcp-key` (the old key is left working; a line says to delete it once nothing uses it). The key gets one org role, the system role "Basic Service API Reader" (`MCP_KEY_ROLE`), the least-privilege role the remote MCP server works with (live 2026-11-17: organization view and view-udfs, Postgres service view, and service view, schema advisor and monitoring view on `instance/*`); query access comes from the Query API endpoint binding (SET-05), not from an org role. Its id comes from `org role list` by exact name, reading only top-level role records (never a role's `actors` or `policies`); a custom role with the same name loses to the `type: system` one; none, or two system roles, is an error that lists the role names seen and asks for `--mcp-role-id` (UUIDs, repeatable), which replaces the lookup. The progress line names the role used: by name, or by id when `--mcp-role-id` was given. (Superseded: D-55's "Member plus Query Endpoints"; the live org has no Query Endpoints role.) The key always gets an IP allow list (default `0.0.0.0/0=agentic-analytics MCP`, because the hosted MCP server and the demo host call from addresses we do not know; a key with no list denies everything). Name `agentic-analytics-mcp-<UTC timestamp>`, the only key detail ever printed (the key id is a secret to `tracing`).
- **Read-only user and role (SET-03).** Over clickhouse-connect as `default` with the admin password (`port 8443`, TLS). The user defaults to `CLICKHOUSE_RO_USER`, else `aa_ro_user` (the role is `analytics_ro`; a distinct user name avoids a user and a role sharing one name). Its password is the one in `.env` when the user name matches, else a new 28-character one with a lower, upper, digit and one of `-_.+` (ClickHouse Cloud's complexity rule; no quoting needed in SQL, `.env` or a shell). `.env` is written before the SQL, so a failed statement is retried with the same password. Statements: `CREATE USER IF NOT EXISTS … IDENTIFIED BY '…'`, `ALTER USER … IDENTIFIED BY '…'`, then `pack_role_sql(pack, "clickhouse", user=…)` split on `;` with comment lines dropped. `role_sql_problems` must return nothing, both for the rendered SQL and for the statements as split for sending, before the admin client is even opened; it refuses `OR REPLACE`, `DROP`, `REVOKE` and `RENAME`, any of which would take `analytics_ro` from the Query API endpoint user (L-7). A failing statement is reported by number and its text up to `IDENTIFIED`.
- **`.env` (SET-04).** Lines are split where `load_dotenv` splits them (`str.splitlines`, so a `\v`, `\x85` or `\u2028` inside a line cannot hide an assignment from the writer). `update_env_file` replaces the first `NAME=`/`export NAME=` line in place, drops later duplicates, appends new names, keeps every other line byte for byte, writes a temp file with mode 600 in the same folder, fsyncs and renames it over the old one, then chmods 600; a symlinked `.env` updates its target. Values with a line break or NUL are refused naming the variable only; values outside a safe set are single- or double-quoted so `load_dotenv` reads them back.
- **No secret in any output (SET-04).** One `SecretBox` per run holds every secret-looking environment value, each password and key id/secret as soon as `clickhousectl` prints it, the generated read-only password, and the Snowflake password and MFA code; every progress line, error and final text passes through it (raw and JSON-escaped forms; PEM private-key blocks removed). Key paths are deliberately not treated as secrets. `cli setup` prints through this box rather than the trace redactor, because the redactor's field rules would hide the key paths and could mangle the public keys in the SQL.
- **Console steps (SET-05).** A fixed template, filled with the service name, the key name (or "whose id is CLICKHOUSE_MCP_KEY_ID in .env" when the key was kept) and `analytics_ro`, printed after a successful run and returned in `--json`. The command never calls `query-endpoint` (the legacy API takes only `sql_console_read_only`/`sql_console_admin`, which would drop the `analytics_ro` settings profile). A closing note says to delete the admin Cloud API key.
- **Snowflake (SET-06).** Keys `admin_key.p8` and `ro_key.p8` (unencrypted PKCS8 RSA-2048) in `--key-dir` (default `~/.snowflake/agentic-analytics/`, mode 700), created with `O_CREAT | O_EXCL` and mode 600, so an existing key is read and reused and never overwritten; `*.pub.txt` (the base64 SubjectPublicKeyInfo) is written only if missing and must match. A public key without its private key, a broken or encrypted key, and a mismatched public file are refused. The bootstrap SQL (saved as `bootstrap.sql` next to the keys) creates `AA_ADMIN_USER` (SYSADMIN, SECURITYADMIN) and `AA_RO_USER` as key-pair service users with `IF NOT EXISTS` plus `ALTER USER … SET RSA_PUBLIC_KEY` (so a rerun installs the current key), grants SYSADMIN imported privileges on `SNOWFLAKE` (reconcile), creates the pack's database and schemas as SYSADMIN (so the loader owns them), runs `pack_role_sql(pack, "snowflake", user="AA_RO_USER")` as ACCOUNTADMIN after `role_sql_problems` passes, grants SYSADMIN usage on `ANALYTICS_XS` (the loader's warehouse) and ends with `SELECT … AS SNOWFLAKE_ACCOUNT`. Default: print it with the Snowsight steps and the `.env` lines; `.env` is not touched. `--run`: account from `--account`, `.env` or a prompt; username by a visible prompt; password and MFA code by `getpass` (Enter = Duo push, no `passcode`); `username_password_mfa` as ACCOUNTADMIN, `execute_string(..., remove_comments=True)`; then `.env` gets the account, both users, both key paths and `SNOWFLAKE_WAREHOUSE=ANALYTICS_XS`; then each user logs in with `SNOWFLAKE_JWT` and `private_key_file` and must read back its own `CURRENT_USER()`.
- **`doctor` MCP check (SET-07).** `SELECT currentRoles() AS roles, getSetting('readonly') AS readonly` through the N1.5 `McpConnection` and `Toolbox` (one call, five rows). Pass only when the role list is non-empty, every role is `analytics_ro`, and readonly is 1 or 2 (D-64: the remote MCP server runs every query with readonly = 2; both refuse writes); otherwise the detail shows the roles and names the console binding. A tool error, an unreadable result or an exception fails the check without crashing doctor, scrubbed of every environment value. `run_doctor` adds the check only when asked (`mcp=` or `check_mcp=True`), so existing N1.2 reports are unchanged; `cli doctor` always asks, and reports `skip` when the MCP variables are missing. It lives in doctor (not in setup) because the binding is a console step that setup cannot verify at the time it prints it.

## Offline vs live
Offline (this node, on fakes): every criterion. Live (owner, not run by the builder): one `setup clickhouse --region …` against the owner's org, the two console steps, `doctor` showing `clickhouse.mcp_role PASS`; `setup snowflake --run` against the trial account, which also confirms the real `--json` shapes and role names. No live test is added.

## Out of scope
Signup (no public API), the MCP toggle and the Query API endpoint binding (no public API, printed instead), deleting the admin Cloud API key or an old MCP key (printed as advice), loading data (N1.3), applying grants for objects that do not exist yet beyond the pack's database and schemas.
