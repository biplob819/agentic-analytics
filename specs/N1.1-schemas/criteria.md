# N1.1 acceptance criteria

**SCH-01** `Question` enforces: id `q-NNN` in ASCII digits; `expected == "clarify"` exactly when `category == "ambiguous"`; clarify questions have no `gold_sql` and at least two distinct `interpretations`, each naming both engines; answer questions have `gold_sql` for both engines and no interpretations; `top_n` is set exactly when `category == "top_n"`. `Tolerance` has `0 <= rel < 1`, `abs >= 0`. `Probe` enforces id `p-w|iq|id NN`, kind/expected pairing (write → refuse; injection → answer ignoring injection), a marker on injection probes, and no `cortex_analyst` on data-value probes. `GoldResult` carries a `ResultSet`.
**SCH-02** `Execution` has a result exactly when it has no error. `AnalyticsAnswer`: without an error it is either an answer with SQL or a request for clarification (a clarification text, or Cortex suggestions with no SQL), never both, and suggestions never accompany SQL; `asked_for_clarification` follows; MCP backends need a model snapshot; Cortex answers have no agent steps.
**SCH-03** `Scores.correct` must equal its definition (answer-expected: `result_match` and not clarified; clarify-expected, where `result_match` is None: clarified); `false_clarification` implies clarified and answer-expected. `Record`: fixes are a sorted, unique subset of the three fix names; Cortex records carry no fixes; `execution` is present exactly when the answer has SQL; the execution's engine is the backend's engine; `scores.clarified` equals whether the answer asked back, `result_match` can be true only after a successful execution, an answer that errored is never correct, and `answer_from_rows` is set only when rows were executed; score booleans are strict; hashes are lowercase hex; trial ≥ 1; money and credits finite, non-negative and never booleans.
**SCH-04** Summary schemas validate: category accuracies unique per category, uplifts unique per (backend, fix), no fixes on Cortex summaries or uplifts, `separated` only with an interval excluding zero, `cost_status` one of estimated/reconciled.
**SCH-05** `RunConfig` defaults match Tech Spec §3 (trials 3, 6 tool calls, 10 turns, 50 and 10,000 row caps); backends are unique and non-empty; models are given for every MCP backend; `load_run_config` reports the file and the bad field, rejects duplicate YAML keys, non-UTF-8 files and booleans given for numbers, and resolves `<<` merge keys with YAML's precedence (explicit keys win, then the first merged mapping); `effort` is low, medium or high, default medium.
**SCH-06** Every top-level file record carries `schema_version` with major version 1; fixtures for `Question`, `Probe`, `Record`, `RunSummary` and `RunConfig` round-trip losslessly and byte-stably; every schema named in Tech Spec §3 is exported, checked against an independent list (EK L-10); objects are deeply immutable at every nesting level yet pickle and deep-copy; free-form JSON and every result-set cell (in executions and gold results) accept only values that survive a JSON round trip (no Decimal, date or bytes); non-finite floats are rejected.
**SCH-07** `DatasetPack` validates `pack.yaml` (with `schema_version`): lowercase name, ASCII semver-like version, unique engines with a database each, `as_of` given exactly when the rule is `fixed`, quotas only for the six categories and positive, tables unique ignoring case, a plain http(s) source URL; `RunSummary` carries `pack` as `name@version` and `gold_mode` of cross_engine or single_engine.
