# Q2.2 — Gold check

**Wave 2. Depends on:** Q2.1, N1.2. **Unblocks:** R3.1, F3.1.

## Goal
Run every answer question's gold SQL on each configured engine through the read-only executors, prove it is consistent across engines, deterministic and free of ties at a top-N cut, select the 100 benchmark questions with the pack's quotas and a fixed seed, and stamp the result with a `gold_check_id` the runner checks before every run (Tech Spec §5 steps 5–7, US9). This node delivers the code half: no account exists, so the measured check itself (and its `docs/measurements/` record) is live-only. The dual-authorship helper (QST-04) is here too; running it is part of Q2.1's open QST-04.

## Where the format lives
R3.1 already defined the gold check file and the id in `run/gold.py` (`GoldCheck`, `compute_gold_check_id`, `write_gold_check`, read by `require_gold`). This node reuses them unchanged and puts the check in a new package, `agentic_analytics.gold`, so the runner's reader and the writer cannot drift: `gold/gold_check.json` is the record R3.1 reads, and `gold/check-<ts>.json` is a byte-identical history copy (never overwritten, so earlier checks stay inspectable).

## Outputs
- `agentic_analytics.gold.check`: `run_gold_check(pack, questions, executors, as_of=, snapshot_sha256=, seed=, only=, write=)`, `check_question`, `rewrite_limit(sql, engine, n)`, `ranking_index(sql, engine)`, `identical`, `cross_engine_mismatch`, `select_questions(passing, quotas, seed)`, `configured_executors(environ)`, `GOLD_ROW_CAP = 200`, `SELECTION_SEED = 20261115`, `GoldConfigError`.
- `agentic_analytics.gold.dual`: `gpt_sol_sql(question_text, ddl=, as_of=, model=)`, `make_gpt_sol()`, `table_ddl(pack)`, `compare_dual(question, gpt_sql, executor, as_of=)`, `dual_authorship(...)`.
- `agentic-analytics gold [--pack] [--only ID] [--verify] [--as-of D | --config run.yaml] [--seed N] [--measurements DIR] [--json]`.
- Files written into the pack: `gold/<engine>/<qid>.json` (`GoldResult`), `gold/check-<YYYYMMDDTHHMMSSZ>.json`, `gold/gold_check.json`.
- Tests in `tests/gold_check/`.

## Design decisions
- **Order of checks per question:** lint issues (Q2.1's `lint_questions`, exact functions included) → run on every engine with `'{as_of}'` bound and `row_cap=200` (error, truncation, empty unless `expects_empty`, rows when `expects_empty` all fail) → second run on the determinism engine → cross-engine comparison → tie check. All failures of a question are collected, not just the first.
- **Strict blocking.** Any failure gives `status: "fail"` and exit 1 (§5 step 5.5, GLD-02). Failing questions are not silently excluded: the owner rules (fix, reword, move, drop) and the check is rerun. The selection is still computed from the passing questions and recorded, so the owner sees what would be kept; a category left short of its quota is one more failure. R3.1 refuses any failed check.
- **Cross-engine comparison reuses S2.1's matcher** (`scoring.result.match_result`) with Snowflake as "predicted" and ClickHouse as "gold": column mapping by name case-insensitively (Snowflake returns uppercase names), else by values; `Tolerance.columns` covered at the question's tolerance, other numbers exact (D-41, D-43); order only for `ordered` questions. Unlike scoring, extra columns are not allowed: the two gold queries must return the same number of columns.
- **Determinism** runs the ClickHouse query twice (the only engine when ClickHouse is not configured) and requires identical results: the same column names and the same rows, exactly (JSON text), as a multiset unless `ordered`. No tolerance: two runs of an exact query on the same data must agree to the bit.
- **Tie check** rewrites only the outermost `LIMIT n` literal, located as the last LIMIT at parenthesis depth 0 in sqlglot's token stream, so the rest of the SQL is executed byte for byte (regenerating SQL from sqlglot's tree would rewrite ClickHouse functions). The LIMIT literal must equal `top_n`. The ranking value is the output column the first ORDER BY key names (by alias or name, else an identical projection expression); every shipped top-N question resolves on both engines. It runs on the determinism engine only: ties are a property of the data, which parity already proves equal on both engines. Fewer than n+1 rows cannot tie.
- **Tie check with tolerance (pre-verification fix).** Rows n and n+1 must differ beyond the question's tolerance when `Tolerance.columns` covers the ranking column (None covers every numeric column, D-41), exactly otherwise; for an `ordered` question every adjacent pair inside the top n must be separated the same way, or the gold order is ambiguous and the question fails. Unordered top-N questions only need the n / n+1 separation.
- **As-of date.** `gold_check.json` records `as_of`, which is part of `gold_check_id`; `require_gold(..., as_of=cfg.as_of)` in the runner refuses (exit 1) a run whose as-of differs.
- **Probe gold.** Every probe with gold SQL runs on each configured engine its backends are scored on (MCP agents: ClickHouse; Cortex: Snowflake), must return 1-200 rows, and with both engines must match exactly. It is stored as `gold/<engine>/<probe id>.json` (`run.gold.ProbeGold`, since `GoldResult` only takes question ids), listed in the record's `probes`, hashed into `gold_check_id`, and `require_gold` returns it with the question gold so the runner scores probes against it.
- **Selection** draws `quota` ids per category with `random.Random(f"{seed}:{category}")` from the sorted passing ids, so it depends only on the seed and the passing set (not on file order), and adding a question to one category never reshuffles another. The seed is fixed (`20261115`), overridable with `--seed`.
- **`sql_hash` is over the executed SQL** (as-of bound), so the gold record pins the as-of date it was computed for. `gold_check_id` is R3.1's: sha256 over the as-of date, the SELECTED questions' JSON (unselected questions never count), the listed probes' JSON, their gold results (id, engine, `sql_hash`, columns, rows) and the snapshot sha256.
- **Gold files** are written for every gold query that ran cleanly, selected or not (R3.1 loads only the selected ones). A failed check still writes its record with `status: "fail"`.
- **`--only ID`** (QST-07, US8) runs the checks for one question (lint, both engines, determinism, cross-engine, tie) and writes nothing; a full `gold` run afterwards brings it into the selection. **`--verify`** keeps R3.1's validate-only behaviour (no SQL; 0 clean, 1 not clean), for users without accounts.
- **CLI inputs.** Executors come from N1.2's `executors_from_env` (after `.env`); the as-of date from `--as-of` or `run.yaml`; the snapshot from the newest `docs/measurements/snapshot-*.json` (missing: exit 1, as `run` does). No engine, a bad date, an unknown `--only` id or a pack that is not a directory: exit 2. A runtime error is exit 2 without a traceback. Single-engine runs are stamped `single_engine`.
- **Dual authorship (QST-04).** `gpt_sol_sql` sends one tool-free turn through an N1.6 adapter: a system prompt with the output format and the exact-function writing rule (otherwise every median would disagree for the wrong reason), and a user turn holding only the ClickHouse `CREATE TABLE` (from the pack's load SQL), the agents' own as-of line (A2.1 `as_of_line`: the date, and "last year" = the last full calendar year before it) and the question text. No gold, id or category is sent. `compare_dual` runs both versions on ClickHouse (row cap 200) and compares them with the same matcher at the question's tolerance; a failing or refused GPT query is a disagreement, not a crash.

## Offline vs live
Offline: every rule against fake executors with planted defects (cross-engine mismatch, tie at the cut, non-deterministic result, failed runs, lint failure, short quota), the file format round-trip through R3.1's `require_gold`, the CLI, and the dual helper with a fake model. Live-only: the actual gold check on both engines (its outcome and the `docs/measurements/` record), the real GPT Sol call, and the `pytest -m gold` check that the bundled gold check is clean (skipped until the first live `agentic-analytics gold` writes it).
