# V5.1 acceptance criteria

**MON-07** A band point is one distinct set of answers, compared only with comparable runs. Every run (`run`, `smoke`, `rescore`) writes a ledger view of its metrics-1 export (`history/metrics.json`) holding only the configurations none of whose answers came from the cache as asked by a run of the same scope or by one that stored no scope (each cache entry stores its asking run's scope, D-125: the fix run's reused baseline answers, a retry rerun, a resume or a second full run add no point; a full run reusing answers the smoke asked records them; a configuration this run asked no answer of, such as in a rescore or a run served wholly from the cache, adds no point; rows of the whole run only when every configuration is new; an uplift with its fix configuration, `all` with descriptions+examples+self_check. A run that stops before recording its history records nothing, and its answers served from the cache on resume add no point: a stated under-count, never a double-count; no run writes outside its own folder and the ledger, and one run at a time per results folder and per answer cache is assumed, as for `results/latest`), every row labelled `scope` (`smoke` or `full`, so the two never compare) and every cost row `cost_status=estimated`, and appends it to EvalKit's run ledger `docs/measurements/runs.jsonl` (B5.7 LED-01, LED-02), stamped with the export's `created_at`; a `reconcile` appends only the reconciled cost rows of those configurations (`cost_status=reconciled`), once per run (`history_reconciled`), never accuracy, so a reconcile is never judged against its own run. Both are judged with the project's `monitoring/gates.yaml` (beside the ledger's `docs/`) (a gated accuracy alarms only downward, `improved` upward); the run log carries the verdict, a repeated view is refused and a ledger error never fails the run. A run outside its alarm band (median ± 2 / 3 spreads from at least 5 comparable runs) is flagged; fewer is `learning`. The trend page shows accuracy with intervals, cost per correct and p95 latency per backend and fix set from EvalKit's history, as `trend.html` beside the dashboard (linked) and the same page in the monitor's artifact. The committed ledger is seeded offline from the stored records, at most one accuracy point per configuration and scope (smoke; baseline and its reconcile; the fix runs' 8 fix configurations and their reconcile), chained, metrics only, each line naming the code that produced it. monitor.yml keeps the history before the run, runs exactly `evalkit history check` on the run's view after the gate under pipefail, and always puts the history line and trend page in its artifact; it stays hand-run. `drift` has its §6.3 row. *Proof:* `tests/monitoring/test_history.py`, `tests/monitoring/test_monitor_workflow.py`, `tests/harness/test_metric_relevance.py`.

**MON-08** `scoring/tolerant.py`'s rules are EvalKit's `sql_match(..., question=, equivalences=)`, behind an adapter that keeps the pre-registered terms (answer-expected questions after a strict miss; `empty_check` only on `expects_empty`; `percent_scale` only with a percent-unit tolerance; per-column exactness; this project's column mapping). Rescoring every stored run offline (5,046 records) changes exactly the one verdict OWNER D-118 recorded (fix runs, q-020, GPT + descriptions, trial 1), with every other `correct`, `correct_strict`, `equivalences` and `result_match` unchanged, written to `docs/measurements/evalkit-0.4-parity-2026-11-18.json` (counts per run, the change before/after and its cause, records sha256) and pinned by a test; the golden run rescores with no change. The published record is regenerated from the rescore (`docs/results/`, `fixruns-evalkit-0.4-2026-11-18.json`, README blocks, figures): only GPT + descriptions moves (92.3% → 92.0%, uplift −4.7 → −5.0, empty_check 4 → 3), the baseline headline does not. *Proof:* `tests/monitoring/test_parity.py`, `tests/test_evalkit_contract.py`, `tests/scoring/test_tolerant.py`, `tests/release/test_readme.py`.

**MON-09** The clarification and false-clarification intervals are EvalKit's clustered `clarification_rates` (cluster = question id, the run's seed and resamples; exact Clopper-Pearson with one trial per question); every point rate equals the stored one on every configuration of every stored run; each interval is within two lattice steps of `aggregate.two_level_interval` at the same seed (measured 0.975); the summary reports EvalKit's interval (OWNER D-100, D-119) and metrics-1 names its method; every byte change in the example and golden exports is explained. *Proof:* `tests/aggregate/test_clarification_intervals.py`, `tests/monitoring/test_parity.py`, `tests/test_evalkit_contract.py`.
